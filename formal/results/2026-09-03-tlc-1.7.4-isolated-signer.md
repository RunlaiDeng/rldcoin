## Model and finite bounds

The model contains one untrusted node and one isolated signer, two conflicting
proposals for one parent instance, node and signer monotonic heads `0..2`, one
crash/restart cycle type, typed proposal/vote requests, exact witness
authorization, signer-local persistent locks, and signature-release state.
The node may submit a second conflicting but valid-looking witness-bound
request, so safety cannot depend on the node honestly remembering its first
request.

Safe vote order is node durable lock, exact witness authorization, typed signer
request, durable signer authorization/monotonic-head update, then signature
release. Safe proposal order is typed request, durable one-parent proposal
lock, then signature release. Raw-byte and wrong-pinned-key probes are rejected
without changing authorization or signature state.

exact-looking authorization for `proposal-b`, crashes, erases the signer lock,
and releases the second signature after restart. The safe model rejects that
same hostile-node sequence because the signer owns and reloads the lock.

## Limitations and open production gates

The model treats typed-request validity, exact witness authorization and
persistence as predicates or atomic transitions. It does not parse bytes,
verify real signatures, count independent witness control domains, model
timeouts or concurrent processes, establish `fsync`/rename semantics, or show
that a software signer cannot be reset with an old disk image. It also does not
model mTLS, endpoint identity, HSM/KMS behavior, secure boot, remote
attestation, key ceremonies, side channels, availability, dynamic validator
sets, BFT view change, or production operations. Those remain explicit
`VALUE_CAP_0` gates.
